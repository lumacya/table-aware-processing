# Table-Aware Processing — разработка модуля

## Задача

Кейс предложил Лаборатория цифрового развития. Существующая RAG-система хорошо работала с документами, но плохо с таблицами. Стандартный чанкинг резал данные по символам — заголовки оставались в одном чанке, данные в другом, итоги терялись. Поиск по таблице деградировал.

Нужен был отдельный модуль обработки `.xlsx` и `.csv` который сохраняет структуру: листы, колонки, типы, диапазоны. На выходе — JSON с чанками пригодными для индексации в RAG, со ссылкой на исходный диапазон вида `Лист1!A2:M51`.

## Исследование

Перед началом работы посмотрели существующие подходы к этой задаче.

**pandas + ручная разметка** — классика. Читаешь `read_excel`, типы определяешь через `dtype`, чанкуешь руками. Минусы — pandas теряет ведущие нули в идентификаторах, не понимает сложных шапок, не группирует по смыслу.

**ydata-profiling** — мощная библиотека профилирования данных. Делает всё что нам нужно по статистике колонок. Но это инструмент для анализа, а не для чанкинга. И зависимости тяжёлые.

**TaPAS, TaBERT** — нейросети обученные на таблицах, понимают семантику. Избыточно для нашей задачи, плюс это тяжёлые модели.

**sherlock** — библиотека на нейросети для определения семантического типа колонок. Распознаёт 78 типов: `phone`, `address`, `company`, `country`. Серьёзно рассматривали и отказались по нескольким причинам:

- Обучена на англоязычных данных. Колонки «ИНН», «КПП», «Заказчик» сеть никогда не видела
- 500 МБ весов модели для модуля чанкинга — много
- Последний коммит в репозитории 2022 года, проект заброшен
- Нам нужно различать 4-5 типов (число, идентификатор, категория, текст), а не 78
- Не вписывается в требуемый стек (pandas, openpyxl, FastAPI)

**LLM-классификация** — спросить GPT/Claude какой тип у колонки. Универсально, но требует API-ключ, латентность секунды на запрос, зависимость от внешнего сервиса. На хакатоне — не вариант.

В итоге выбрали **эвристический подход со скорингом признаков**. Подробнее об этом дальше.

## Архитектура

Спроектировали модульную архитектуру с чёткой ответственностью каждого слоя:

```
loader → analyzer → strategies → processor
   ↓        ↓          ↓            ↓
 чтение   типы +    нарезка     результат
          профиль   на чанки
```

**`loader.py`** — чтение файлов. Определяет формат, кодировку, разделитель. Для xlsx с непростой структурой ищет настоящую строку начала таблицы (бывает что первые строки — это шапка документа, а не таблицы).

**`analyzer.py`** — анализ структуры. На вход pandas DataFrame, на выход `SheetMeta` с метаданными колонок: типы, статистика, top-N значений, предупреждения.

**`type_detection.py`** — отдельный модуль определения типов через скоринг. Вынесли в отдельный файл потому что логика нетривиальная и хотелось изолировать.

**`strategies/`** — три стратегии чанкинга через паттерн Strategy Pattern. Базовый абстрактный класс плюс две конкретные реализации.

**`processor.py`** — главный фасад. Склеивает всё воедино, выбирает стратегию, собирает результат.

**`utils.py`** — общие утилиты. Excel-нотация, выбор колонки для группировки.

**`api/main.py`** — тонкая обёртка FastAPI над модулем. Один эндпоинт `/process` который принимает файл и параметры, возвращает JSON.

### Почему такая структура

Каждый модуль решает одну задачу. Тесты пишутся на каждый слой отдельно. Если завтра нужно добавить поддержку Parquet — меняем только `loader.py`. Если нужна новая стратегия чанкинга — добавляем класс в `strategies/`, не трогая остальное.

Pydantic-модели в `models.py` — единый язык между слоями. Loader возвращает `dict[str, DataFrame]`, analyzer возвращает `dict[str, SheetMeta]`, стратегии возвращают `list[Chunk]`. Никакой неявной структуры данных, всё типизировано.

## Технологии и почему именно они

**pandas** — обязательное требование задачи. Стандарт индустрии для табличных данных, векторизованные операции работают быстро на больших данных.

**openpyxl** — чтение xlsx. У нас две задачи на которых она работает: основное чтение через `pd.read_excel(engine='openpyxl')` и быстрый поиск merged cells через прямое чтение XML из ZIP-архива (об этом ниже в разделе про производительность).

**xlrd** — для устаревших `.xls` файлов. Используется как fallback.

**Pydantic v2** — модели данных с валидацией. Альтернативы — dataclasses (нет валидации) или TypedDict (нет runtime проверки). Pydantic даёт всё сразу: типизация, валидация, автоматическая сериализация в JSON. FastAPI его использует «из коробки».

**FastAPI** — для HTTP API. Обязательное требование задачи. Автоматическая документация через Swagger UI, валидация запросов через Pydantic.

**chardet** — определение кодировки CSV. Российские файлы часто в `cp1251`, не в `utf-8`. Без этого половина CSV читалась бы битой.

**ruff** — линтер. Заменяет связку `black + flake8 + isort`. Быстрый, написан на Rust.

**pytest** — тесты. Стандарт.

## Умное определение типов через скоринг

Это центральная техническая часть проекта. Расскажу подробно.

### Проблема с прямым подходом

Простая идея: «если все значения проходят регулярку для числа — это число». Не работает на реальных данных. Например:

- ИНН `0274975591` — это число? По форме да. По смыслу — идентификатор, нужно хранить как текст с ведущим нулём. Если потерять ноль — данные испортятся.
- ОКПД2 `28.13.11.110` — это число? Содержит точки. По форме это десятичная дробь. По смыслу — иерархический код товара.
- Цена `1 234 567,50` — это число? Да, но pandas сразу не распарсит из-за пробелов и запятой.

Хардкодом эти случаи не закрыть — каждый новый домен принесёт свои паттерны (СНИЛС, артикулы, ТН ВЭД, кадастровые номера).

### Решение через скоринг

Идея простая: каждый признак колонки даёт скор для каждого возможного типа. Финальное решение — сумма скоров.

Реализация в `type_detection.py`:

**`ColumnProfile`** — dataclass с признаками колонки. Считается один раз. Признаки:

- `unique_ratio` — доля уникальных значений
- `mean_length`, `std_length` — статистика длин
- `has_leading_zeros` — есть ли значения с ведущим нулём
- `numeric_ratio` — доля значений которые парсятся как число
- `entropy` — информационная энтропия распределения
- `name_has_id_keyword` — имя колонки содержит «инн», «кпп», «id», «код» и подобные
- `name_has_price_keyword` — имя колонки содержит «цена», «стоимость», «сумма»

**`TypeScorer`** — возвращает скоры для каждого типа на основе профиля. Логика для типа `identifier`:

```
+0.5 если имя колонки содержит ключевое слово идентификатора
+0.4 если есть ведущие нули
+0.3 если длина значений постоянная (std < 2.0) и >= 5 символов
+0.2 если уникальность > 80%
+0.2 если значения числовые но длинные (>= 8 цифр)
-0.4 если имя колонки про цену
```

Аналогичные правила для `numeric`, `categorical`, `text`, `mixed`.

**Финальное решение** — тип с максимальным скором. Если выиграл `identifier` — возвращаем `TEXT` (идентификаторы храним как текст). Если выиграл `numeric` — определяем `INTEGER` или `FLOAT` по наличию точки.

### Почему это не хардкод

Вопрос, который мы задавали себе: чем это отличается от написания миллиона `if-else`? Принципиально.

В хардкоде каждое новое требование = новое правило. Правил растёт линейно с количеством случаев, в какой-то момент они начинают конфликтовать.

В скоринге каждый признак — независимая функция. Финальное решение — результат суммирования множества слабых сигналов, а не один жёсткий if. Добавить новый edge case = добавить один признак в профиль и одну строку в скорер. Не нужно ничего переписывать.

### Что получилось

На реальных файлах от заказчика модуль правильно определил:

- ИНН (10 цифр), ИНН физлица (12 цифр) → `text`
- КПП (9 цифр) → `text`
- ОГРН (13 цифр) → `text`
- ОКПД2, ТН ВЭД → `text`
- Цены с дробной частью → `float`
- Даты в форматах `YYYY-MM-DD`, `DD.MM.YYYY` → `date`
- Регионы (повторяющиеся значения) → `categorical`
- Длинные описания товаров → `text`

Без единого жёсткого if под конкретный домен. Скоринг универсальный.

## Стратегии чанкинга

Три стратегии через паттерн Strategy Pattern.

**`row_based`** — простая нарезка по N строк. Каждый чанк содержит фиксированное число строк плюс шапку. Параметры:

- `chunk_size` — максимум строк в чанке (по умолчанию 50)
- `max_cells_per_chunk` — защита от широких таблиц. Если в таблице 200 колонок, эффективный размер чанка автоматически сжимается. Формула: `min(chunk_size, max_cells // col_count)`
- `max_bytes_per_chunk` — нарезка по байтам. Полезно для RAG где есть лимит на размер контекста LLM. Строки не разрываются — если одна строка сама по себе превысила лимит, она идёт отдельным чанком с пометкой `oversized_row: True`

**`semantic`** — группировка по значениям ключевой колонки. Например все строки с регионом «Москва» в один чанк, все с «Санкт-Петербург» — в другой. Колонка для группировки выбирается автоматически по приоритету типов: `categorical → date → datetime → boolean`. Для группировки берём колонку с минимальным числом уникальных значений среди подходящих.

Если группа больше 200 строк — она дробится через `row_based` с сохранением `group_value` в metadata каждого подчанка. Это важно — крупная категория не превращается в гигантский чанк.

**`auto`** — модуль сам решает. Если в листе есть подходящая колонка для группировки — `semantic`. Если нет — `row_based`. На практике AUTO нужен потому что пользователь не всегда знает структуру файла.

### Контекст в каждом чанке

Согласно требованиям, в каждом чанке должно быть всё что нужно для понимания без обращения к остальным:

- `sheet_name` — имя листа
- `columns` и `column_types` — заголовки и типы колонок
- `row_start`, `row_end` — диапазон строк
- `source_ref` — ссылка в Excel-нотации, например `Лист1!A52:M101`
- `content` — текстовое представление данных таблицей с разделителями
- `summary` — краткое описание для retrieval: имя листа, колонки, превью первых трёх строк, числовая статистика по колонкам

Текстовая проекция в `summary` нужна для embedding-поиска. Когда RAG-система ищет по запросу «средняя цена в Краснодарском крае», она находит чанк по embedding и видит в summary что в этом чанке про Краснодарский край и есть статистика.

## С какими проблемами столкнулись и как решали

### Проблема 1: ИНН становился числом

В первой реализации ИНН типа `0274975591` определялся как `INTEGER` (после строгой regex-проверки на цифры). Pandas терял ведущий ноль, число становилось `274975591`. Для системы которая ищет компанию по ИНН это критично.

Первая попытка решения — хардкод: «если имя колонки содержит "ИНН" — text». Работает на этом конкретном случае, не работает на завтрашнем «номер договора» или «артикул».

Вторая попытка — эвристика по длине: «если все значения числовые и одинаковой длины — это идентификатор». Работает на 90% случаев, ломается на ИНН физлиц (12 цифр) которые соседствуют с ИНН юрлиц (10 цифр) в одной колонке.

Финальное решение — скоринг описанный выше. Идентификатор определяется по комбинации: имя колонки + ведущие нули + постоянная длина + высокая уникальность. Каждый признак сам по себе слабый, вместе работают.

### Проблема 2: производительность на 100k строк

Первая реализация обрабатывала файл `stress_lots.xlsx` (100 000 строк) около минуты. Это было неприемлемо.

Сначала добавили замеры через `time.perf_counter()` на каждом этапе. Получили картину:

```
load:     8.4с
analyze: 13.5с
chunking: 7.0с
```

13 секунд на анализ — самое медленное. Добавили замеры по колонкам. Оказалось каждая колонка обрабатывается ~0.1с — итого 1.6с на все. То есть 11 секунд уходит ВНЕ цикла по колонкам. Добавили замеры на остальное:

```
header_rows:  0.001с
merged_cells: 7.5с    ← вот оно
warnings:     0.04с
```

Виновник найден. Функция `has_merged_cells` загружала через openpyxl весь Excel-файл в память чтобы проверить наличие merged cells. Для файла на 100k строк это 7.5 секунд.

Поняли что проверка merged cells через полное чтение — оверкилл. xlsx это ZIP-архив, merged cells лежат в `xl/worksheets/sheet1.xml`. Прочитали XML напрямую через `zipfile`, проверили наличие тега `<mergeCell` через поиск подстроки. Время: с 7.5с до 0.086с — ускорение в 87 раз.

Дальше оптимизировали `_df_to_text` — заменили `df.iterrows()` (Python-цикл) на векторизованный `df.apply(' | '.join, axis=1)`. Несколько раз меньше времени на больших данных.

Для байтовой нарезки добавили предвычисление массива `row_bytes_list` через `df.apply` — раньше каждый шаг цикла вызывал `_estimate_row_bytes(df.iloc[i])`, что было крайне медленно.

В `type_detection` добавили сэмплирование: для серий больше 5000 элементов берём случайную выборку. Тип колонки определяется по паттернам, а не по количеству — все 100k значений анализировать не нужно.

В analyzer убрали лишние вызовы — `_get_numeric_stats` теперь вызывается только для числовых типов, а не для всех колонок.

Итоговые цифры на том же файле:

```
load:     7.4с (openpyxl читает xlsx — это нижняя граница, оптимизировать нечего)
analyze:  2.3с (было 13.5с)
chunking: 7.0с (math: 2000 чанков × 3мс = 6с, нормально)
итого:   ~17с (было ~60с)
```

Ускорение в 3.5 раза. Главный урок — мерять прежде чем оптимизировать. Без замеров мы бы потратили день на ускорение типизации, не зная что проблема в одной строке кода с openpyxl.

### Проблема 3: сложные многострочные шапки

В файле `small_analytical.xlsx` (аналитическая справка) первые 8 строк содержали шапку документа: «Аналитическая справка», «Заказчик: ...», «ИНН: ...». Только на 9-й строке начинались настоящие заголовки таблицы.

Pandas из коробки берёт первую строку как заголовок и получает `Unnamed: 0`, `Unnamed: 1` — потому что первая строка пустая. Все колонки безымянные, типы определяются по случайным значениям.

Решение — функция `_find_header_row` в loader. Через openpyxl читаем строки и ищем первую где заполнено больше 30% ячеек. Это эвристика, но она работает на практике: настоящий заголовок таблицы заполнен почти полностью, мета-строки имеют 1-2 заполненных ячейки.

После находки строки — перечитываем файл с правильным `header=N`. Теперь колонки получают свои настоящие имена.

### Параллельную обработку рассмотрели и отказались

Думали про параллельную обработку групп в semantic стратегии через `ThreadPoolExecutor` или `ProcessPoolExecutor`. Это могло бы дать ускорение на больших файлах с многими группами.

Не сделали по двум причинам:

- ThreadPoolExecutor ограничен GIL — для CPU-bound операций как у нас выигрыша почти нет
- ProcessPoolExecutor требует сериализации DataFrame через pickle между процессами. На 100k строк сама сериализация может съесть весь выигрыш

Это был бы «флип монеты» — может помочь, может нет. Без замеров на конкретной машине не угадать. Решили что 3.5x ускорение от точечных оптимизаций — надёжный результат, а параллелизм — рискованная ставка.

## Известные ограничения

Честно перечисляем что модуль не делает или делает плохо.

**Многострочные шапки с merged cells.** Наш `_detect_header_rows` определяет максимум 2-строчную шапку. В реальных файлах бывают шапки в 3-4 строки с объединёнными ячейками которые группируют колонки по смыслу (например «Поставщик: цена | срок | контакт» где «Поставщик» это объединённая ячейка над тремя). После разворачивания merged cells часть колонок остаётся `Unnamed`. Модуль это видит и добавляет в warnings, но автоматически не разрешает. Решение требует читать XML напрямую и реконструировать структуру — большая отдельная задача.

**Несколько таблиц на одном листе.** Если на одном листе две независимые таблицы с пустыми строками между ними — модуль обработает их как одну. Разделение требует анализа структуры данных, мы такого не делаем.

**Скрытые строки и колонки.** openpyxl читает их как обычные. Если в Excel колонка скрыта — мы её всё равно увидим. Не критично для большинства случаев, но стоит знать.

**Точность определения типа на маленьких выборках.** На колонке из 5 значений эвристика менее надёжна — мало признаков для скоринга. Для очень маленьких таблиц возможны ошибки. Для таблиц от 50 строк работает уверенно.

**Производительность чтения xlsx.** Узкое место — это openpyxl. На 100k строк она тратит 7+ секунд только на чтение. Альтернативы: `python-calamine` (Rust под капотом, быстрее в разы), но это новая зависимость вне утверждённого стека. Оставили openpyxl.
