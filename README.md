# Table-Aware Processor

Python-модуль обработки табличных файлов (`.xlsx`, `.xls`, `.csv`), который сохраняет структуру таблицы и режет её на чанки по строкам и смысловым группам, а не по символам — для индексации в RAG-системах.

Каждый чанк несёт с собой имя листа, заголовки и типы колонок, диапазон строк и ссылку на исходное место в нотации Excel (`Лист1!A2:M51`).

> **Как принимались решения** — какие альтернативы рассмотрены и отвергнуты, почему выбран скоринг вместо нейросетевой классификации, как искалось узкое место производительности: [DEFENSE.md](DEFENSE.md).
> **Формат выходного JSON** — [CONTRACT.md](CONTRACT.md).

## Задача

Кейс Лаборатории цифрового развития, весенний хакатон университета «Дубна», 2026.

В существующей умной базе знаний все файлы разбивались на чанки одинаково — по фиксированному числу символов. Для связного текста это работает, для таблиц — нет: заголовки колонок попадают в один чанк, данные в другой, строки с итогами и единицы измерения теряются. Найденное значение «1 250 000» невозможно интерпретировать — цена это, объём или код. Качество поиска по табличным данным деградирует.

Нужен был модуль, который разбирает XLSX и CSV с сохранением структуры (листы, колонки, типы, диапазоны) и отдаёт JSON с самодостаточными чанками, пригодными для индексации и для ссылки на источник в ответе.

## Контекст и роль

Команда из трёх человек, два дня разработки в удалённом формате и очная защита перед комиссией. Проект разделён на три блока: загрузка и извлечение данных из файлов, ядро обработки, HTTP-интерфейс и тестирование.

Автор этого репозитория отвечал за **ядро обработки** — `analyzer`, `type_detection`, `strategies`, `processor`, модели данных: определение типов колонок, профилирование, предупреждения о качестве данных и все стратегии чанкинга. Загрузчик файлов и FastAPI-обёртка разрабатывались другими участниками команды.

## Возможности

- Чтение `.xlsx`, `.xls`, `.csv` с автоопределением кодировки (`cp1251` в том числе) и разделителя
- Автопоиск настоящей строки заголовков под мета-шапкой документа
- Определение 10 типов колонок скорингом признаков: ИНН, КПП, ОГРН и коды ОКПД2 сохраняются как `text` с ведущими нулями, цены в российском формате распознаются как `float`
- Профилирование колонок: доля пропусков, уникальность, min/max/avg для числовых, top-N значений для категориальных
- 5 видов предупреждений о качестве данных: смешанные типы, пустые строки, подозрительные итоги в последней строке, объединённые ячейки, откат стратегии
- Три стратегии чанкинга (`row_based`, `semantic`, `auto`) и три способа ограничить размер чанка — по строкам, ячейкам, байтам
- HTTP API на FastAPI со Swagger-документацией

```json
{
  "id": "registry__Лист1__rows_0_49",
  "sheet_name": "Лист1",
  "strategy": "row_based",
  "row_start": 0,
  "row_end": 49,
  "columns": ["Предприятие", "ИНН", "ОГРН", "Дата внесения"],
  "column_types": {
    "Предприятие": "text",
    "ИНН": "text",
    "ОГРН": "text",
    "Дата внесения": "datetime"
  },
  "source_ref": "Лист1!A2:D51",
```

`summary` — текстовая проекция для векторного поиска: по запросу «средняя цена в Краснодарском крае» RAG-система находит нужный чанк по embedding, а `source_ref` позволяет сослаться в ответе на точный диапазон исходного файла.

## Использование

### Как библиотека

```python
from table_processor import process_file, ChunkStrategy

result = process_file(
    "data.xlsx",
    strategy=ChunkStrategy.AUTO,
    chunk_size=50,
)

print(f"Стратегия: {result.strategy}")
print(f"Всего чанков: {result.total_chunks}")

for chunk in result.chunks:
    print(f"{chunk.id} | {chunk.source_ref} | строк: {chunk.row_count}")
```

### Через HTTP API

```bash
uvicorn api.main:app --reload --port 8005
```

Swagger: <http://localhost:8005/docs>

```bash
curl -X POST "http://localhost:8005/process?strategy=auto&chunk_size=100" \
  -F "file=@data.xlsx"
```

### Параметры обработки

| Параметр | Дефолт | Описание |
|---|---|---|
| `strategy` | `auto` | `row_based`, `semantic` или `auto` |
| `chunk_size` | `50` | Максимум строк в чанке |
| `max_cells_per_chunk` | `10000` | Защита от широких таблиц |
| `max_bytes_per_chunk` | `None` | Нарезка по байтам |

## Как это работает

### Определение типов через скоринг

Прямолинейная проверка «проходит регулярку числа — значит число» на реальных данных ломается: ИНН `0274975591` по форме число, но по смыслу идентификатор, и потеря ведущего нуля портит данные; код ОКПД2 `28.13.11.110` выглядит как десятичная дробь; цена `1 234 567,50` — число, но pandas не разберёт его из-за пробелов и запятой.

Жёсткие правила вида «имя колонки содержит ИНН → текст» не масштабируются: каждый новый домен приносит СНИЛС, артикулы, ТН ВЭД, кадастровые номера, правила множатся и начинают конфликтовать.

Вместо этого по колонке один раз считается профиль признаков — доля уникальных значений, средняя длина и её разброс, наличие ведущих нулей, доля разбираемых как число, энтропия распределения, ключевые слова в имени колонки. Каждый признак добавляет или отнимает баллы каждому типу-кандидату, побеждает тип с максимальной суммой. Новый пограничный случай закрывается одним признаком в профиле и одной строкой в скорере, а не переписыванием цепочки условий.

Для колонок длиннее 5000 значений профиль строится по случайной выборке — тип определяется паттернами, а не количеством.

### Стратегии чанкинга

**`row_based`** — нарезка по N строк. `max_cells_per_chunk` автоматически сжимает чанк на широких таблицах, `max_bytes_per_chunk` режет по объёму, не разрывая строки: строка, превысившая лимит в одиночку, уходит отдельным чанком с пометкой `oversized_row`.

**`semantic`** — группировка по значениям ключевой колонки (все строки по «Москве» в один чанк, по «Санкт-Петербургу» в другой). Колонка выбирается автоматически по приоритету `categorical → date → datetime → boolean`, среди подходящих берётся с минимальным числом уникальных значений. Группа больше 200 строк дробится через `row_based` с сохранением значения группы в метаданных каждого подчанка.

**`auto`** — при наличии подходящей группировочной колонки применяется `semantic`, иначе `row_based`.

## Производительность

Оптимизация велась по замерам `time.perf_counter()` на каждом этапе конвейера. Самым медленным оказался анализ структуры, причём цикл по колонкам занимал лишь 1,6 с из 13,5 — остальное уходило на проверку объединённых ячеек, которая грузила через openpyxl весь файл в память ради одного признака.

XLSX — это ZIP-архив, и сведения об объединённых ячейках лежат в XML листа. Проверка переписана на прямое чтение XML из архива: **7,5 с → 0,086 с, ускорение в 87 раз.**

Дальше — точечные оптимизации: `iterrows()` заменён векторизованным `apply`, размеры строк для байтовой нарезки предвычисляются одним проходом, статистика считается только для числовых колонок.

Стресс-файл на 100 000 строк:

| Этап конвейера | До, с | После, с |
|---|---|---|
| Чтение файла | 8,4 | 7,4 |
| Анализ структуры | 13,5 | 2,3 |
| Чанкинг | 7,0 | 7,0 |
| **Итого** | **28,9** | **16,7** |
